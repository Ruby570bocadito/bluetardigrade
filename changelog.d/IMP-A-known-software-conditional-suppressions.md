Suppressions accept conditions: a suppression entry may carry `when`, a list of event-field conditions (field/operator/value) that must ALL hold for the alert to be silenced, evaluated with the same operators the rule engine uses. This is the "suppress this exactly" case — one noisy invocation shape of an otherwise useful rule stops firing while every other invocation keeps alerting. Conditional entries never silence aggregated alerts (kill-chains, beaconing, volumetric), which carry no single event to evaluate.

The engine now ships a known-software list (`-known-software`, `known-software.example.yaml`): entries matched by executable-image glob and/or SHA-256 label events with `enrichment.known_software`. The events stay stored and searchable, but the baseline stops reporting them as novelties, the noise report stops counting them (with a `known_software_events` honesty counter) and rules may opt out with `exclude_known_software: true`. The live entry count appears in `/api/stats` (`known_software_active`).

GET /api/ad/posture now serves the stored 0-100 score in the `score` field; previously the envelope carried the field but always returned null (SEG-A finding, fixed together with under-lock reads of the hub's wiring fields).
