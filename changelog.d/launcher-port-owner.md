- **The launchers say who holds each port and no longer mistake another program for the console.** `sf-console` and `sf-status` only checked whether something answered on 7777, 3003 and 3000, so a video render serving on :3000 made `sf-console` print "console already running" while `sf-status` called it stopped. Each port is now traced to its process: this installation's (by path or pid file) shows as running with its pid, another program is named with the script it runs (`node.exe (remotion-cli.js, pid 21516)`), and a process started as administrator is reported as such. When another program holds the console port, `sf-console` moves the console to the next free port and remembers it in `run\console.port`, so `sf-start`, `sf-status` and the browser follow it; an explicit `-ConsolePort` that is taken stops with a suggestion instead. Every start confirms what it did ("engine started", "hub started", "console started (:3001)"), `sf-status` prints a coloured table with the console address, `sf-stop` only reports leftovers of its own, and the new `sf-console -Restart` restarts just the console. After `sf-start` creates the first account it restarts a running console itself, so sign-in applies at once instead of asking for `sf-stop` and `sf-start`.
