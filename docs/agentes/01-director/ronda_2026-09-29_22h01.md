## 6. Decisiones del Director (las dos que el propietario marcó pendientes)

### 6.1 Escritura de supresiones vía API — DECISIÓN: SÍ, pero opt-in por flag, autenticado y ruidoso

La API de solo lectura fue una simplificación honesta de v0.1 y ha llegado a su límite: la vista Supresiones de la consola es un post-it de lectura, el ciclo de vida de alertas (sección 7C) lo necesita, y editar YAML a mano en el host del motor no escala ni para un laboratorio. Diseño que ordeno implementar:

1. **Flag opt-in:** el motor solo acepta escrituras si arranca con `-api-write` (o `SF_API_WRITE=1`). Sin la flag, `POST/DELETE /api/suppressions` devuelve `403` con cuerpo accionable (cómo habilitarla, igual que el 401 actual nombra el token). Degrade loudly por defecto: la superficie de escritura no existe a menos que el operador la pida.
2. **Misma auth que el resto:** Bearer obligatorio (la escritura hereda el gate `/api/*` existente; sin token configurado y bind no-loopback, la escritura ni siquiera con flag se rechaza con aviso en arranque).
3. **Validación idéntica al YAML:** las entradas pasan por el mismo validador de `suppress.Manager` (rule_id no vacío, host opcional, expires RFC 3339); una entrada malformada se rechaza con 400 y el detalle, nunca se recorta en silencio.
4. **Persistencia bidireccional honesta:** la fuente de verdad sigue siendo `suppressions.yaml` (el fichero que el hot-reload ya vigila). La API escribe el fichero atómicamente (temp+rename) y el reload existente lo recoge; así el fichero editado a mano y la API no divergen y no hay un segundo estado oculto. Si el fichero no es escribible, error 500 ruidoso, no un 200 vacío.
5. **Auditoría:** cada escritura loguea `WRITE suppressions add/remove rule=X host=Y by=api` con timestamp — el operador debe poder reconstruir quién silenció qué y cuándo.
6. **Guard del spec:** el spec OpenAPI se actualiza con las operaciones de escritura marcadas como gated por la flag; el guard existente se extiende para verificar que el 403 documentado coincide con el código, igual que hoy hace con el 401.

Esta decisión desbloquea la UI de fase 2 del propietario (crear/quitar supresiones desde la consola con feedback real) y el ciclo de vida de alertas (7C-1), que reutiliza el mismo mecanismo de escritura para notas de operador.

### 6.2 Runners estables para bench nocturno en CI — DECISIÓN: job programado con umbrales consultivos, no bloqueantes

Los runners hospedados de GitHub son ruidosos: un umbral duro de latencia sobre `ubuntu-latest` produce falsos positivos semanales y termina desactivándose, que es peor que no tenerlo. Diseño que ordeno implementar:

1. **Job `bench-nightly`** con `schedule: cron` (nocturno) separado del CI de PR: compila el motor, arranca loopback con auth, corre `cmd/bench -n 2000 -rate 1000` (los parámetros ya documentados del README) y escribe el resultado JSON (p50/p90/p99, throughput, counters) como artifact del run.
2. **Historial commiteado:** el job añade (o actualiza por PR nocturno automático, a decidir por ruido) una línea en `docs/bench/history.jsonl` con fecha y cifras — la serie temporal es el activo, no el número aislado del día.
3. **Regresión = desviación estadística, no umbral fijo:** alarma si p99 del día > 2× la mediana de los últimos 7 días (con mínimo de 5 puntos para opinar). La alarma abre un issue, no rompe un check de PR.
4. **Etiqueta de ruido obligatoria en el informe del job:** "runner hospedado, cifras para tendencia, no para absolutos" — el p99 absoluto fiable seguirá viniendo del bench en hardware controlado (los 319-434 µs ya publicados).
5. **No bloquea PRs jamás.** El CI de PR mantiene su coste actual; esto es observabilidad de tendencia.
