## 2. Aterrizaje de la decisión 6.1 — escritura de supresiones vía API

La decisión estaba tomada y fundamentada en la sección 6.1 del informe de ronda 5; esta ronda la convierte en código que respeta **cada uno de sus seis puntos**:

| Punto de la decisión | Implementación |
|---|---|
| 1. Flag opt-in `-api-write` / `SF_API_WRITE=1` | Flag nueva del motor (flag gana sobre env, como todas); sin ella, `POST`/`DELETE /api/suppressions` responden **403 con cuerpo accionable** que nombra la flag, igual que el 401 nombra el token |
| 2. Misma auth que el resto | Las rutas se registran tras el mux con bearer existente → 401 heredado sin credential; y **en arranque se niega a armarse** si la API no tiene token y el bind no es loopback (aviso sonoro) — escrituras no autenticadas más allá de loopback no existen |
| 3. Validación idéntica al YAML | Nueva `suppress.ValidateEntry` + `NormalizeEntry` (mismas reglas: no vacuo, expires RFC 3339; host normalizado a minúsculas); `parseFile` refactorizado para usar el mismo código — **una sola fuente de verdad de las reglas**, no dos validadores que divergen |
| 4. Fichero como fuente única de verdad | `suppress.SaveFile` escribe **atómicamente** (temp en el mismo directorio + `rename`, `fsync`, modo preservado; fichero nuevo a **0600** siguiendo el estándar del hardening del store) y el handler recarga inmediatamente — el cambio es vivo al instante, sobrevive reinicios, y el hot-reload de 15 s encuentra el mismo contenido; entradas expiradas **no se pierden** al reescribir (`Manager.All()` devuelve el set completo de disco) |
| 5. Auditoría | Cada escritura loguea `WRITE suppressions add/update/remove rule=X host=Y by=api (file ...)`; los fallos de escritura son ruidosos (log + 500) y **sin fuga de internals** al cliente, mismo estándar que `storeQueryError` |
| 6. Guard del spec extendido | `check_openapi.py` ahora (a) **escanea todos los `.go` de `internal/api`**, (b) compara **operaciones (método, ruta)** en ambas direcciones, y (c) exige que toda operación POST/DELETE documente el **403 con el ejemplo byte-a-byte** contra el cuerpo del código, espejo exacto del check del 401; self-test ampliado de 10 a **13 variantes** |

### 2.1 Contrato de la superficie (resumen operable)

- `POST /api/suppressions` — cuerpo `SuppressionEntry` (`rule_id`, `host`, `reason`, `expires`); **upsert por par (rule_id, host)**: publicar un par existente actualiza reason/expires en vez de duplicar. Responde **200** con el estado nuevo (misma forma que el GET, para que la consola haga round-trip con un solo payload).
- `DELETE /api/suppressions?rule_id=…&host=…` — elimina **solo** las entradas cuyo par coincide exactamente (la entrada sin host solo se elimina con query sin host, y viceversa: sin expansión wildcard silenciosa); **404** si nada coincidió, **400** si ambos parámetros van vacíos.
- Errores: **400** con el detalle del validador (entrada malformada nunca se recorta en silencio), **401** (bearer, heredado), **403** (superficie no armada), **500** ruidoso (fichero no escribible; detalle al log del motor).
- Sin flag: 403 en ambos métodos; **con bind no-loopback y sin token el arranque se niega a armar** las escrituras (aviso explícito en el log de arranque).
- Loopback sin token: la escritura funciona (coherente con la API de lectura abierta en loopback — mismo criterio de siempre).

## 4. Hallazgos nuevos de esta ronda

### H1 (MEDIO, mitigado parcialmente): `make ci` roto por deriva de toolchain en el paso `bunx tsc` del hub

`make ci` ejecuta `cd web/console-service && bun install --frozen-lockfile && bun test && bunx tsc --noEmit`. El proyecto **no declara `typescript`** en sus devDependencies, así que `bunx` descarga el último TypeScript publicado — en este entorno, **7.0.2** (compilador nativo con semántica distinta) — y el paso falla con decenas de errores que no corresponden a ninguna regresión del código. Mitigación aplicada en esta ronda: **`typescript: "5"` fijado en devDependencies** (resuelve 5.9.3 local, `bun.lock` actualizado, 3 líneas). Así `bunx tsc` es determinista y usa el binario local.

Con 5.9.3 el paso sigue fallando — ver H2 — pero ahora de forma **reproducible y con errores accionables**, que es la única base honesta para arreglarlo.

### H2 (MEDIO, asignado): los errores estrictos del tsc del hub son preexistentes, no de esta ronda

Con el TypeScript fijado, `tsc --noEmit` sobre `web/console-service` reporta ~30 errores en 4 ficheros (`hub.ts:80` parámetros implícitos `any`; `hub-state.ts:174` `offlineStats` sin las claves `correlator_*`; `hub.test.ts` y `http-ui.test.ts` con `body` `unknown`, esperas `async` usadas como `boolean`, etc.). **Ninguno proviene de esta ronda** (no toqué ese paquete) y explica por qué las certificaciones previas decían "hub 41/41 + tsc de consola OK": el `bun test` del hub siempre pasó, pero el `tsc --noEmit` del hub **no constaba como certificado en ninguna acta**. Es una laguna real de `make ci` que conviene cerrar cuanto antes: los tests de Bun no sustituyen al typecheck.

**Asignación:** ola de 02-implementaciones (sección 5) — es su paquete, el fix es mecánico y el listado exacto de errores sale del propio comando. 03-pulimiento puede aprovechar para institucionalizar `smoke_r6` como `scripts/dev-tests/suppress_write_smoke.sh` con las convenciones de `smoke_auth.sh`.

### H3 (BAJO, observación): `bun install --frozen-lockfile` falló una vez por red

Durante la batería, la primera invocación de `bun install --frozen-lockfile` falló (red) y el reintento resolvió limpio ("no changes", `bun.lock` intacto en git). Sin acción; se anota porque el CI hospedado puede tragar el mismo ruido.

### H4 (INFO, para la ola de consola): el hub no proxya REST de escritura

`web/console-service` multiplexa lectura (SSE/socket.io + bridge de analista) y **no** reenvía métodos POST/DELETE al motor. La UI de supresiones de fase 2 debe hablar directamente con la API del motor (con el token del operador) o el bridge debe extenderse a métodos de escritura con su propia autorización. Decisión de diseño que corresponde a la ola de consola; la arquitectura de 6.1 (403 accionable, bearer, auditoría) ya deja el contrato listo para ambas opciones.
