# Ronda — 2026-09-29 17h32 UTC — Implementaciones

## Resumen

Ronda corta y quirúrgica dedicada íntegramente al último pendiente de
la cola de Pulimiento: **el lockfile de Rust del sensor**. Con él, el
árbol del repositorio queda completo y las builds del sensor pasan a
ser reproducibles bit a bit para cualquiera que clone el repo.

## Contexto

El informe de Pulimiento (`03-pulimiento/ronda_2026-09-29_19h12.md`,
pendiente #3) dejaba constancia de que `sensor/Cargo.lock` seguía sin
generar por falta de host con toolchain Rust. El propio `.gitignore`
documentaba la política correcta: para un crate binario el lockfile se
commitea (reproducible builds), y quedaba "pendiente hasta entonces".

## Trabajo realizado

### 1. `sensor/Cargo.lock` generado y commiteado

- Toolchain: `rustup` perfil minimal, **stable 1.98.1** (cargo 1.98.1,
  rustc 1.98.1).
- `cargo generate-lockfile` en `sensor/` → **55 paquetes** fijados a la
  última versión compatible con las restricciones del manifiesto
  (`anyhow 1`, `serde 1` + derive, `serde_json 1`; `ferrisetw 1` queda
  registrado como dependencia de target Windows).
- Formato lockfile v4 (el estándar actual de cargo).

### 2. Verificación de que el lockfile es real, no decorativo

- `cargo build --release --locked` → **OK** (perfil release con
  `lto = true` + `strip = true`). La flag `--locked` fallaría si el
  lockfile no estuviera exactamente sincronizado con `Cargo.toml`, así
  que esta es la garantía de reproducibilidad, no solo la existencia
  del fichero.
- Binario producido y smoke-tested: `security-sensor` sin argumentos →
  `unknown argument` + usage correcto (parsing vivo).
- En Linux el binario **se niega a correr** con el mensaje de diseño
  ("ETW telemetry is only available on Windows; refusing to run without
  real data") — comportamiento correcto y deliberado, coincide con lo
  documentado en README (línea ~319): el sensor no simula datos.
- Los 16 warnings de la build Linux son el dead code esperado de un
  crate multiplataforma (`transport.rs`/`normalize.rs` tienen rutas que
  solo el colector Windows invoca). No se ha tocado código para
  silenciarlos: añadir `#[allow(dead_code)]` global escondería señales
  útiles en la build real de Windows.

### 3. Corrección colateral: comentario obsoleto en `Cargo.toml`

El comentario sobre las dependencias decía "*the --simulate mode needs
no kernel access*" — un modo `--simulate` que **ya no existe**: la ronda
de Bugs/Seguridad eliminó la simulación del sensor Rust (el diseño
actual, documentado en el propio `main.rs`, es negarse a correr sin
telemetría real). El comentario ahora describe la realidad: el crate
compila en cualquier OS (parsing, normalización, transporte) pero el
binario se niega a ejecutarse fuera de Windows. Sin cambios semánticos
en el manifiesto.

## Verificación

- `cargo build --release --locked` → verde (3.2s con caché; ~10s frío).
- `go build ./...` + `go vet ./...` + `go test ./...` → verde (la ronda
  no toca Go, verificado por hygiene).
- `git status`: solo `sensor/Cargo.lock` (nuevo) + `sensor/Cargo.toml`
  (comentario). `sensor/target/` sigue ignorado correctamente.

## Pendientes que pasan a la cola

- **[BAJA] Warnings de dead code en builds no-Windows:** opcionales;
  si algún día molestan, la solución limpia es `#[cfg]`-gating en las
  funciones de transporte usadas solo por el colector, no `allow`
  globales.
- **[BAJA] Renovar lockfile cuando suban versiones:** procedimiento
  normal (`cargo update -p <crate>` puntual, o `cargo update` completo
  en rondas de mantenimiento).

## Notas de método

- Misma lección de las rondas anteriores aplicada: verificación por
  comandos con salida comprobable (`--locked`, exit codes, `git status`)
  y no por inspección visual.
- Sin colisiones con otras rondas: el área tocada (crate Rust) no se ha
  modificado desde la ronda de auth de ingest de Bugs/Seguridad.
