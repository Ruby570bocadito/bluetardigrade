# Ronda — 2026-09-29 17h51 UTC — Implementaciones

## Resumen

Ronda con dos entregas: (1) cierre del residual de warnings de dead code
en builds no-Windows del sensor, que al investigarlo **destapó un bug de
mucha mayor entidad**, y (2) reescritura del colector ETW de Windows
contra la API real de `ferrisetw`, que **nunca compiló**: el código
original llamaba a funciones que no existen en ninguna versión del crate
(0.1.0 → 1.2.0).

## El hallazgo: el colector Windows era código que no podía funcionar

### Cómo se destapó

La cola residual decía: "*warnings de dead code en builds no-Windows;
la solución limpia es `#[cfg]`-gating en las funciones de transporte*".
Al preparar ese fix, el cross-check con `cargo check --target
x86_64-pc-windows-msvc` (target nunca antes usado en este proyecto)
falló con `E0433/E0432/E0599` en `collector.rs`: no existían
`ferrisetw::event::process_start_event::ProcessStartEvent`,
`ferrisetw::query::{BuildEventStream, EventStream}` ni
`Provider::kernel_process()`.

### Verificación de que NO es un problema de versión

- `Cargo.lock` fija `ferrisetw 1.2.0`; su árbol `src/` real (registrado
  en `~/.cargo/registry`) no exporta módulo `event` ni esos símbolos.
- Se sondearon **todas** las versiones publicadas del crate (índice de
  crates.io: 0.1.0-yanked, 0.1.1, 1.0.0, 1.1.0, 1.2.0): 1.0.0 verificada
  por compilación de sonda y 0.1.1 por inspección directa del código
  fuente — **ninguna tuvo jamás esa API**.
- Conclusión: `collector.rs` fue escrito contra una API inexistente y
  jamás fue compilado. En Linux era invisible porque el módulo está
  `#[cfg(target_os = "windows")]`-gated; ningún agente anterior llegó a
  hacer cross-check de Windows.

### Hipótesis errónea registrada y corregida

Primero se atribuyó el fallo a "*ferrisetw solo soporta MSVC*" — falso:
los mismos errores de símbolos aparecían en ambos targets Windows porque
el problema era el código, no el target. Queda constancia como recordatorio
de método: verificar la hipótesis re-ejecutando, no racionalizar el
primer resultado.

## El fix: collector.rs reescrito contra la API real (1.2.0)

### Cambios de código

- `sensor/src/collector.rs` — reescrito (77 → 121 líneas) con el patrón
  de los ejemplos del propio crate (`user_trace.rs`, `kernel_trace.rs`):
  - `UserTrace::new().named(...).enable(Provider::by_guid(...))` +
    `start()` → `(trace, TraceHandle)`, y `UserTrace::
    process_from_handle(handle)` bloqueando en el hilo actual (import de
    `TraceTrait` — el método vive ahí, no en `RealTimeTraceTrait`).
  - Proveedor elegido: **Microsoft-Windows-Kernel-Process** (manifest,
    GUID `22fb2cd6-…`), evento 1 `ProcessStart`: a diferencia de los
    eventos kernel DSTART, **sí trae CommandLine**, campo que el diseño
    del sensor necesita.
  - Callback `FnMut(&EventRecord, &SchemaLocator)`: parseo con
    `Parser::create` + `try_parse::<T>("ProcessID"/"ParentID"/
    "ImageName"/"CommandLine")`, degradación gracia por campo (pid
    obligatorio; ppid 0 y CommandLine ausentes se omiten en la
    serialización vía los `skip_serializing_if` existentes).
  - `TraceError` (de ferrisetw) no implementa `Display` ni
    `std::error::Error` en 1.2.0 → los errores se mapean explícitos con
    `map_err(|e| anyhow!("{e:?}"))` en lugar de `?`.
  - **Contrato de salida intacto**: mismos `EventJson`/`ProcessJson`,
    mismo NDJSON, mismas etiquetas; `normalize.rs` y `transport.rs` sin
    cambios funcionales.
- `sensor/src/normalize.rs` — 4 `#[allow(dead_code)]` quirúrgicos con
  comentario `// phase 1:` en el scaffolding aún sin consumidor
  (`HashesJson`, `NetworkJson`, `TYPE_PROCESS_TERMINATE`,
  `TYPE_NETWORK_CONNECT`). Nada de allows globales.
- `sensor/src/main.rs` — `mod normalize`/`mod transport` ahora
  `#[cfg(target_os = "windows")]` (solo el colector los usa): el build
  Linux queda con **cero warnings** sin tocar su comportamiento.

### Lo que este entorno NO puede probar (honestidad de cobertura)

La sesión ETW en un Windows real (creación del trace, recepción de
eventos, calidad de los nombres de propiedad `ParentID`/`CommandLine` en
todas las versiones de Windows soportadas) requiere un host Windows.
El compile-check contra AMBOS targets Windows valida tipos, imports y
firmas — no la ejecución. Pendiente explícito: smoke test en Windows
(el mismo que el proyecto ya necesita para el instalador `.ps1`).

## Notas de método

- El residual "menor" de la cola escondía el hallazgo más grave del
  proyecto hasta la fecha: **todo cfg-gated es código no verificado** y
  debe cross-chequearse aunque no pueda ejecutarse. `cargo check
  --target` es barato y ahora está demostrado que encuentra bugs que
  `cargo test ./...` (Go y Rust host) no puede ver.

  simulado del sensor y la dependencia de marca): la política del
  proyecto de verificar todo por compilación/ejecución real, no por
