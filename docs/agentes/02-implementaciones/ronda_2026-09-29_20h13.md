## Resumen ejecutivo

Detectar es la mitad del trabajo; la otra mitad es trabajar la cola. Hasta hoy una alerta existía como payload inmutable: idéntica en el log JSON, el webhook y la SSE, pero sin identidad propia (la consola sintetizaba `event_id:rule_id`) ni estado operatorio — un SOC real no puede operar así. Esta ronda da a cada alerta un `id` criptográfico del motor, un ciclo de vida de tres estados (`new` implícito → `acknowledged` → `closed`, con `new` como reabrimiento explícito), notas de triaje con atribución libre (`by`, honestamente documentado como NO autenticado: el token compartido no identifica usuarios), persistencia write-through atómica en fichero, y propagación en vivo de extremo a extremo. El API deja de ser estrictamente read-only: triaje es LA excepción, documentada como tal en spec, README y comentarios de paquete.

## Cambio 1 — Identidad de alerta (`internal/alert`, `internal/api`)

- `alert.Alert` gana el campo `id` (16 hex de `crypto/rand`, 8 bytes = 64 bits; fallback a timestamp si la entropía del sistema falla — una alerta sin id rompería los lookups de lifecycle en silencio). `NewID()` exportado.
- Asignación en los tres puntos de entrada: `Raise` (buildAlert), `Emit` (completions del correlador) y `RecordAlert` como red de seguridad (toda alerta que entra en el anillo del API lleva id, la construyan quien la construya — tests incluidos).
- El spec OpenAPI convierte `id` en **required** del schema `Alert` con pattern `^[0-9a-f]{16}$`; la descripción documenta que los payloads crudos (log, webhook, frame SSE de alerta) siempre lo llevan, y que los campos `status*` son overlay de lectura.
- Hub: `mapAlert` usa el `id` del motor cuando existe (fallback al sintetizado `event:rule` para motores viejos — compatibilidad sin promesa).

## Cambio 2 — Store de triaje (`internal/lifecycle`, nuevo paquete)

- `Store` con estados `new|acknowledged|closed`, nota (≤2000 chars) y `by` (≤200). `Set/Get/Count` bajo mutex; validación explícita de status/longitudes con errores accionables (el API los convierte en 400).
- **Persistencia write-through atómica**: temp file + rename en cada mutación (el triaje es de ritmo humano; el coste es cero y ninguna nota puede perderse en un corte). Sin path = solo memoria (contrato estable, documentado en el flag).
- **Cap FIFO de 10.000 entradas** (`MaxEntries`): el fichero no crece sin cota en un motor longevo; el estado del triaje más antiguo es el menos valioso.
- **Fichero malformado = FATAL al arrancar**, el mismo estándar fail-loud de supresiones: empezar la ronda con todo "new" desharía trabajo de triaje que el operador cree registrado. Versión de formato (`version: 1`) para poder evolucionar; entradas duplicadas colapsan a la última escritura.
- La fuente de verdad de ESTADO es el store; la del CONTENIDO de la alerta sigue siendo el anillo. El merge es read-time: los estados sobreviven a la expulsión del anillo por diseño.

## Cambio 3 — Superficie API (`internal/api`)

- Ruta `POST /api/alerts/{id}/status` (la 11ª servida): valida el id contra el pattern del motor, cuerpo ≤8KiB (`http.MaxBytesReader`), status válido, longitudes de nota/by → 200 con la entrada almacenada; 400 con cuerpo `{"error":"..."}` accionable para id malformado, JSON roto, status desconocido o nota larga. El objetivo NO necesita estar en el anillo: una alerta expulsada se puede cerrar igualmente (el store es la fuente de verdad de estado).
- **Éxito = broadcast SSE `alert_lifecycle`** con la entrada: los consumidores vivos se actualizan sin sondear.
- `GET /api/alerts` y el export (JSONL/CSV) devuelven `alertView` (embedding con flatten JSON): `status` SIEMPRE presente (default explícito `new` — el lector nunca special-casea campos ausentes) + `status_note/status_by/status_at` cuando hay decisión. El CSV gana las columnas `id`, `status`, `status_note`, `status_by` (contrato actualizado en spec y tests).
- El middleware Bearer existente cubre la ruta nueva automáticamente (el guard del spec lo verifica: 10 operaciones gated ahora, la 401 con challenge documentada). Sin `-api-token`, el endpoint queda abierto en loopback como el resto — coherente con el modelo de amenaza documentado.
- `SetLifecycle(store)`: el hub crea un store en memoria por defecto en `New` (el POST siempre funciona, reset al reiniciar); el motor inyecta el de fichero al arrancar. Un `nil` en el setter se ignora (un botón que 500ea es peor que un estado que resetea).

## Cambio 4 — Cableado del motor (`cmd/engine`)

- Flag `-lifecycle` (default `./alert-lifecycle.json`, resuelto contra el directorio de instalación con el modismo `resolveDataFile` existente; vacío = memoria). Fichero malformado al arrancar = `log.Fatalf` (ver Cambio 2).
- Línea de arranque honesta: `alert lifecycle: N triage states loaded from <path>` (o el aviso de memoria-pura cuando se desactiva).
- `.gitignore`: `alert-lifecycle.json(.tmp)` es estado de ejecución del operador, nunca se commitea.

## Cambio 5 — Hub y consola (triaje en vivo)

- **Hub (`web/console-service`)**: nuevo módulo `lifecycle.ts` con el validador puro del payload consola→hub (`parseLifecycleRequest`: id 16-hex, status del vocabulario, límites de nota/by — mismas reglas que el motor, errores en el idioma de la consola). El bridge consume el frame SSE `alert_lifecycle`; el hub parchea la copia del anillo y re-emite `console:alert_lifecycle` (una vez por POST: no hace falta change-only). **El proxy de escritura vive en el hub** (`lifecycle:set` con ack): el navegador jamás habla con el API del motor directo — el token se queda server-side, la misma política que cada credencial del sistema. Validación antes de tocar el motor, errores con ack estructurado.
- **Consola (`web/console`)**: chips de estado en cada fila (`reconocida` azul / `cerrada` verde — "new" NO renderiza chip: la ausencia ES el estado nuevo, un chip en cada alerta fresca sería ruido), panel de triaje expandido con nota opcional (≤2000), botones Reconocer/Cerrar/Reabrir con spinner de in-flight y error inline (`role="alert"`) que nunca se traga. La búsqueda libre ahora también cubre las notas de triaje. La lista se actualiza vía `console:alert_lifecycle` (no vía el ack: la actualización viaja por el canal, una sola fuente de verdad). Reduced-motion y estilos existentes respetados; cero dependencias nuevas.

## Integración con la ola de rediseño (rebase `bdcf5b6..d23f913`)

Durante la ronda, main avanzó 27 commits (CLI cobra/charm con `legacyMain` byte-compatible, store SQLite opt-in `internal/store`, consola "pro SOC" con lectura DIRECTA del API vía proxy same-origin `/api/engine`, hub reescrito en `hub.ts`/`hub-state.ts`). El rebase resolvió 11 ficheros en conflicto; decisiones de convergencia:

- **cmd/engine**: la ronda adoptó la arquitectura CLI; el flag `-lifecycle` y el cableado del store de triaje se portaron a `run.go` (options + flagSet + runEngine), manteniendo el contrato del flag idéntico.
- **internal/api**: el hub fusionado lleva `store` Y `lifecycle` lado a lado; `GET /api/alerts` y el export aplican el overlay de triaje en AMBOS modos (anillo y store) — el estado no depende de qué backend responda. `RecordAlert` conserva el backstop de id (toda alerta en el anillo lleva la clave de lifecycle).
- **Consola**: la ola eliminó el bus socket.io para telemetría (lectura directa + SSE con EventSource). El puerto del triaje sigue esa arquitectura: `lib/lifecycle.ts` con `postAlertStatus()` vía el mismo proxy, listener SSE `alert_lifecycle` en `use-engine-stream`, chips + TriagePanel en la vista rediseñada (compacto y tabla). El proxy `[...path]/route.ts` reenvía POST solo para `/api/alerts/{id}/status`; todo lo demás sigue 405 (read-only).
- **Hub socket.io**: queda como superficie legacy/analytics; `onLifecycle` se cablea igualmente (parche de anillo + re-emit `console:alert_lifecycle`) para que el contrato del socket no pierda la nueva frame.
- **Deuda del árbol entrante reparada** (el job Console del CI en GitHub estaba en failure ANTES de esta ronda): `offlineStats` sin los 3 campos correlator (hub-state.ts), fixtures de `HubStats` incompletos (http-ui.test, hub-state.test), `pollUntil` síncrono usado con predicados async, `json()` devolviendo `unknown` sin casts (hub.test) — `bunx tsc --noEmit` y `bun test` vuelven a verde en `web/console-service`.

- El escenario 8 del smoke_lifecycle destapó una verdad de diseño que el test unitario no muestra: tras reiniciar, el anillo de alertas (memoria) está vacío, así que la vista mezclada no puede mostrar el estado — **el fichero garantiza hoy el registro de auditoría; la visibilidad estado+alerta juntas llega con SQLite (fase 2)**. El smoke lo documenta y verifica lo que SÍ promete el contrato (no se promete de más ni en tests ni en README).
