### 2. Lockfiles de `web/console`: deriva real detectada y eliminada

- **Hallazgo (evidencia, no teoría):** el manifest declara `"@types/node": "^24"`, `package-lock.json` resolvía `24.19.0`, pero `bun.lock` seguía clavado en `26.6.3` (el pin exacto de una ronda anterior de Implementaciones, del que el manifest ya se había movido). Es decir: los dos lockfiles no solo convivían — ya **discrepaban entre sí y con el manifiesto**. Un `bun install --frozen-lockfile` sobre el árbol tal cual estaba habría fallado; un clon fresco recibía un lockfile que no correspondía al manifest.
- **Decisión:** `bun` es el toolchain que usan todos los docs (README raíz y `web/console/README.md`) y no hay CI que use npm (no existe `.github/`). Por tanto `bun.lock` es el canónico: regenerado con `bun install` (ahora resuelve `@types/node@24.19.0`, coherente con el rango `^24`) y `package-lock.json` eliminado (3.670 líneas). La política queda documentada en una nueva sección "Lockfile policy" de `web/console/README.md`, incluyendo cómo regenerar un lock de npm localmente si alguien lo necesita (`npm install --package-lock-only`); la eliminación es trivialmente reversible desde git si Implementaciones declara una necesidad concreta de npm.
- **Contexto:** este era el pendiente nº 2 de la ronda previa del rol y una observación repetida en su informe anterior; tras dos rondas sin decisión del área propietaria, se ejecuta desde el rol de higiene de dependencias con la evidencia de deriva delante.
- **Verificación:** `bunx tsc --noEmit` limpio y `bun run build` de producción completo (prerender estático OK) con la resolución nueva.
- **`console-service`:** sin cambios; solo tiene `bun.lock` y no presenta anomalías.
