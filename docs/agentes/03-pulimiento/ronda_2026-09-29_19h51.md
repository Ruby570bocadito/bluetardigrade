## Detalle por cambio

### 1. Deriva del spec OpenAPI detectada y corregida (`docs/api/openapi.yaml`)

- **Cómo se detectó:** auditoría sistemática del commit entrante `ae55c04` ("ingest: expose ingest_rejected in /api/stats + pipelined auth regression test"). El spec fue validado campo a campo contra un motor vivo por Implementaciones en su ronda 19h00, pero el contador nuevo llegó después: `statsPayload` tiene 14 campos y el esquema `Stats` del spec solo declaraba 13. Es exactamente el tipo de desincronización que la validación manual no puede prevenir cuando el código avanza.
- **Corrección 1 — `ingest_rejected` añadido** (lista `required` + propiedad con descripción): conexiones cerradas por fallar el handshake de auth del ingest (token erróneo o ausente, `AUTH` contra un motor sin token, timeout de auth) — la señal visible de sondeos contra un bind remoto; cero con auth desactivada en loopback. Redactado desde el código (`internal/ingest/ingest.go:79-81`, `checkAuth`) y el comentario de wiring de `internal/api/api.go:83-85`.
- **Corrección 2 — descripción de `dropped` reescrita:** decía "events discarded because the ingest channel was full". Falso: `s.events <- ev` es un send **bloqueante** (contrapresión, no descarte); `dropped` cuenta en realidad las líneas que el decoder rechaza (`decode(line)` con error, `ingest.go:172-175`), tras lo cual la conexión recibe un ack de error y sigue abierta. La descripción antigua describía un comportamiento que el código no tiene — documentación aspiracional, precisamente lo que este proyecto se empeña en evitar.
- **Verificación:** parseo YAML correcto; las 8 rutas del spec coinciden con las servidas por `api.go`; los 14 campos del esquema coinciden con los wire tags del struct; prueba negativa del validador contra la versión previa del spec (git stash) → 2 hallazgos exactos. Detalle en §2.

### 2. `scripts/dev-tests/` — verificación E2E dentro del repo (nuevo directorio)

Implementaciones (ronda 19h00, sección "Para Pulimiento") propuso traer los scripts de prueba (receptor HTTP, batería del instalador) a `scripts/dev-tests/` "en alguna ronda" para que futuros agentes repliquen las validaciones E2E. Esta es esa ronda. Se incluyen solo las herramientas **verificadas por ejecución en este entorno**:

- **`check_openapi.py`** — validación estructural del spec contra el código fuente, sin motor en marcha: (a) toda ruta registrada en `api.go` está declarada en el spec y ninguna de más; (b) el esquema `Stats` coincide campo a campo con los wire tags de `statsPayload` (struct sin `omitempty`: todo campo se emite siempre, luego todo es `required`). Probado en ambas direcciones: verde sobre el spec corregido, y **falla con los 2 hallazgos exactos** sobre el spec anterior a esta ronda. Un validador que solo sabe decir OK no vale nada; este atrapó la deriva real de `ae55c04`.
- **`webhook_receiver.py`** — receptor HTTP mínimo para probar la entrega de webhook del motor, con tres modos verificados: interactivo (resumen JSON al interrumpir), `--expect N --timeout S` (exit 0 solo si llegan exactamente N; probado con 3/3 → 0, y con 2/3 → exit 1), y `--secret` (401 sin cabecera, 200 con `Authorization: Bearer` correcto — preparado para cuando la salida webhook gane auth, riesgo MEDIA #1 del Director, hoy sin dueño activo tras la retirada del assigned de 04). Stdlib de python3, solo loopback.
- **`smoke_auth.sh`** — smoke de autenticación del ingest con **binarios reales** (compila `cmd/engine` y `cmd/devsensor` si no se le pasan rutas): los 4 escenarios documentados en el README por Bugs/Seguridad — (1) tokens coincidentes → eventos fluyen (`events_total=19, ingest_rejected=0` en esta ejecución); (2) token erróneo → sensor rechazado con el error del ack y `events_total` inmóvil; (3) sensor con token contra motor sin token → fallo inmediato con guía de configuración; (4) bind `0.0.0.0` sin token → advertencia de arranque. Ejecución completa: **4/4 escenarios OK, exit 0, cero procesos residuales**.
- **Lecciones de método del smoke (para quien lo mantenga):** la primera versión del script tenía dos bugs propios que las pruebas destaparon y convierten en funcionalidad: (a) `kill $!` sobre el subshell de arranque no alcanzaba al binario del motor — motores huérfanos retenían puertos y provocaban fallos confusos a mitad de ronda; ahora el subshell hace `exec` del binario, el PID capturado ES el motor y el cleanup es real; (b) el bucle de espera de la API del escenario 3 no fallaba si el motor no arrancaba; ahora cada espera valida y falla con el log apuntado. Además: pre-flight de puertos con mensaje accionable (`SMOKE_PORT`/`SMOKE_API_PORT`), puertos de escenarios separados (+10/+20) para no depender de kills previos, y `SMOKE_KEEP=1` para conservar artefactos en `/tmp` al depurar. Verificado también el caso límite del método del Director: el fallo del escenario 3 de la primera ejecución se diagnosticó por conteos y logs, no por display.
- **`scripts/dev-tests/README.md`** — tabla script/qué valida/qué requiere, uso desde la raíz del repo y las notas de robustez. La batería del instalador PowerShell (19 casos de Implementaciones) **no** se incluye: requiere pwsh y un host Windows para verificarse, y este rol solo commitea lo que ejecuta; queda anotado para quien tenga el entorno.
