## Cambios (qué se pulió, por qué, ficheros, impacto)

### POL-A-docs-12 — diagrama «System overview»

- **Qué:** el diagrama mermaid de `docs/ARCHITECTURE.md` tenía 3
  clases de deriva factual:
  1. **Endpoint subgraph** decía «ETW Kernel-Process providers»
     pero el sensor Rust consume 4 providers desde el commit
     `0a4a8aa` (Kernel-Process, Kernel-Network, Kernel-Registry,
     DNS-Client). Misma deriva que la fila «Telemetry» del feature
     inventory tenía antes de la ronda 3: leer el diagrama y la
     fila juntos era contradictorio.
  2. **Pipeline del motor** omitía componentes que existen y son
     visibles para el operador desde `/api/stats` y la consola:
     - Enriquecimiento: `intel` (offline threat lists, paquete
       `internal/intel`), `baseline` (per-host novelty,
       `internal/baseline`), `fleet` (machine inventory +
       heartbeats, `internal/fleet`). Los tres se cablean en
       `cmd/engine/run.go` alrededor de las líneas 133/318/330.
     - Alerta: `forensic` (evidence bundles, `internal/forensic`,
       cableado en run.go:194), `lifecycle` (alert triage,
       `internal/lifecycle`, run.go:229), `suppressions` (operator
       allowlist, `internal/suppress`, run.go:177). El fan-out de
       alertas en run.go:658 los recorre.
     - Sinks de alerta: el diagrama tenía un solo nodo «SIEM/SOAR
       collector» etiquetado sobre el webhook, pero el motor tiene
       3 paths separadas: `webhook` (`internal/webhook`,
       run.go:556), `notify` (`internal/notify`, run.go:581) y
       `siem` (Elastic + Splunk, `internal/siem`, run.go:603/626).
     - Action sink: `respond` (active response, kill_process,
       `internal/respond`, run.go:500) no aparecía.
  3. **Webhook node** estaba etiquetado «SIEM/SOAR collector» pero
     el webhook es un path separada de los sinks SIEM. La
     etiqueta ocultaba que hay 3 paths.
- **Por qué:** el diagrama es lo primero que un lector de
  ARCHITECTURE.md ve tras la intro. Si miente, el lector se hace
  un modelo mental incompleto. La deriva del endpoint subgraph era
  la misma que ya corregí en la fila «Telemetry» — de hecho,
  dejarla hacía que el documento se contradijera a sí mismo.
- **Ficheros:** `docs/ARCHITECTURE.md` (diagrama mermaid
  reescrito, +13 nodos y sus edges).
- **Impacto:** el diagrama ahora muestra los 4 providers ETW, los
  3 componentes de enriquecimiento (intel/baseline/fleet), los 3
  componentes de alerta (forensic/lifecycle/suppress), los 3 sinks
  de alerta (webhook/notify/siem) y el sink de acción (respond).
  Verificado con un script Python que comprueba que todo node ID
  referenciado en un edge está definido (cero huérfanos).

### POL-A-docs-13 — párrafo bajo el diagrama

- **Qué:** el párrafo bajo el diagrama decía «The unified event
  schema (`pkg/model`) is the master contract: sensors emit it,
  the engine validates and enriches it, rules index it, interfaces
  consume it.» Era cierto pero incompleto: no nombraba los
  productores reales (Rust ETW sensor, Go SOC collector,
  external producers) ni los consumidores reales (API local, web
  console, SIEM/notification sinks). Lo ampliado a: «The unified
  event schema (`pkg/model`) is the master contract: the Rust ETW
  sensor, the Go SOC collector and any external producer all emit
  it; the engine validates, enriches and indexes it; the local
  API, the web console and the SIEM/notification sinks all consume
  the alerts derived from it. Sensors and collectors never branch
  the schema — a new telemetry source is a new producer of the
  same events, not a new wire format.»
- **Por qué:** el párrafo es el cierre conceptual del diagrama;
  nombrar los productores y consumidores reales hace explícito el
  contrato de schema que el diagrama solo implica.
- **Ficheros:** `docs/ARCHITECTURE.md` (1 párrafo ampliado).
- **Impacto:** el lector entiende que añadir una fuente de
  telemetría es añadir un productor del mismo schema, no un
  formato nuevo.
