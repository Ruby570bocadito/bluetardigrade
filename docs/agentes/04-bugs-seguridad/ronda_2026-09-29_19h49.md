# Informe de ronda — Agente de Bugs y Seguridad (ronda de canales autenticados)

- **Fecha y hora de la ronda:** 2026-09-29 19:49 (Europa/Madrid); integrada sobre `main` con los 11 aterrizajes paralelos ya en el remoto.
- **Contexto:** continuidad directa de la cola de este rol tras la ronda de verificación cruzada (`ronda_2026-09-29_19h14.md`), que dejaba dos hallazgos [MEDIA] sin corregir (webhook sin cabecera de autenticación, rotación del token de ingest) y una recomendación transversal ("todo canal salvo el loopback exige auth explícita"). Esta ronda cierra el primero y extiende el estándar a los dos canales que aún no lo cumplían: la API local (7778) y el webhook de salida.

## Resumen ejecutivo

Tres cierres aterrizan en esta ronda: (1) **webhook con token portador** (`-webhook-token` / `SF_WEBHOOK_TOKEN`): cada POST lleva `Authorization: Bearer`, de modo que un receptor alcanzable desde más hosts que el motor pueda rechazar entregas falsificadas en lugar de ingerir alertas falsas en el SIEM; (2) **API 7778 con token portador opcional** (`-api-token` / `SF_API_TOKEN`): todas las rutas `/api/*` responden 401 sin credencial válida, `/api/health` queda abierta a propósito por ser la sonda de vida que usan el propio motor, el puente de la consola y los checks de disponibilidad; (3) **el instalador exige token para abrir el firewall** (`-Firewall` sin `-IngestToken` se niega y retira cualquier regla heredada de installs pre-gate), además de persistir también el token de webhook. El estándar de la casa queda ahora simétrico: loopback sin fricción por defecto, todo canal que trasciende el host exige credencial explícita con comparación en tiempo constante y fallos ruidosos.

## Aportes efectivos de esta ronda

### 1. Webhook de salida con autenticación portador — SEVERIDAD: media (cierra el hallazgo [MEDIA] de la ronda 19h14)

- **Descripción:** el POST al receptor no llevaba ninguna cabecera de autenticación. Un collector abierto y alcanzable desde la red es un canal de envenenamiento: cualquiera puede inyectar alertas falsas en el SIEM/SOAR.
- **Solución y archivos:** `internal/webhook/webhook.go` (campo `token`, `SetToken`, cabecera `Authorization: Bearer` en cada intento, incluidos los reintentos y el drain de apagado); `cmd/engine/main.go` (flag `-webhook-token`, env `SF_WEBHOOK_TOKEN`, flag gana — misma precedencia que el token de ingest; línea de arranque que indica el estado de la auth). `install.ps1` persiste el token en `tools\config\webhook.token` (`-WebhookToken`, vacío limpia) y lo propaga al autostart; la entrada de Run pasa `-webhook-token` al motor.
- **Cómo verificar:** `go test ./internal/webhook/` (2 tests nuevos: cabecera exacta con token, ausencia total sin token) y el smoke e2e (Test C abajo).

### 2. API 7778 con token portador opcional — SEVERIDAD: media (estándar "todo canal exige auth" ahora completo)

- **Descripción:** la API entrega todos los eventos y alertas (anillos de 1000/256, exports, stream SSE). Enlaza en loopback por defecto, pero al abrirse con `-api 0.0.0.0:7778` quedaba sin credencial: cualquier proceso del host o host remoto que alcance el puerto lee la telemetría completa sin rastro.
- **Solución y archivos:** `internal/api/api.go` (`SetToken` + middleware `auth` sobre el mux: comparación en tiempo constante con `crypto/subtle` en cada petición, 401 JSON con log ruidoso por rechazo, exención explícita de `/api/health`); `cmd/engine/main.go` (flag `-api-token`, env `SF_API_TOKEN`, flag gana; mensaje de arranque y WARNING si la API escucha fuera de loopback sin token — espejo exacto del aviso de ingest); `web/console-service/bridge.ts` + `index.ts` (el puente envía la cabecera en probe, sync inicial, stream SSE y polls de stats leyendo la MISMA variable `SF_API_TOKEN`, así el despliegue protegido necesita una sola entrada de entorno); `docs/api/openapi.yaml` (`securitySchemes.bearerAuth` + nota de opcionalidad); README con la sección "API authentication".
- **Decisión de diseño — salud abierta:** `/api/health` responde `{"status":"ok","mode":"engine"}` y nada más; dejarla abierta evita romper la sonda del propio motor (`apiHealthy`), la del puente y cualquier check de disponibilidad, sin filtrar telemetría. El resto de rutas, incluido el stream SSE, exigen la cabecera (el puente usa `fetch`, no `EventSource`, así que puede enviarla).
- **Cómo verificar:** `go test ./internal/api/` (test nuevo: 401 sin cabecera, 401 token erróneo, 401 esquema erróneo, 200 con token, health abierta, datos reales con token) y smoke Test A.

### 3. Instalador: el firewall exige token de ingest — SEVERIDAD: media-alta (puerta de seguridad en la superficie de Windows)

- **Descripción:** `-Firewall` abría TCP 7777 aunque no hubiera token configurado. El propio comentario de la función reconocía que "an unauthenticated NDJSON ingest must never be reachable" — pero solo restringía perfiles domain/private: cualquier equipo del segmento LAN (doméstico o de empresa) podía inyectar eventos.
- **Solución y archivos:** `install.ps1`:
  - `-IngestToken <t>` persiste el token en `tools\config\ingest.token` (vacío limpia; validación 8–128 caracteres sin espacios ni comillas, porque el token viaja en la línea de comandos del autostart y en el handshake); sin el flag se reutiliza el persistido, así `sf-update` conserva la config.
  - `-Firewall` **se niega** a crear la regla sin token (mensaje con el comando exacto para remediarlo) y **retira** una regla preexistente heredada de un install anterior a la puerta — coherencia: si hoy no se puede crear, no puede sobrevivir una de ayer.
  - `Register-Autostart` arranca el motor con `-token '<t>'`; la línea de resumen indica "ingest auth: ENABLED" sin imprimir el secreto.
  - `scripts/windows/sf-console.ps1`: el motor auto-arrancado por la consola ahora lee el token persistido (antes solo la entrada de autostart lo llevaba; dos rutas de arranque con configuraciones distintas es una trampa de diagnóstico).
- **Migración:** quien usara `-Firewall` sin token y ejecute `sf-update` verá la regla retirada con un aviso claro; sus sensores remotos dejan de entrar hasta configurar `-IngestToken` — que es exactamente el comportamiento deseado para un canal de inyección sin credencial.
- **Limitación documentada (aceptada para v0.1):** el token persistido vive en un fichero del perfil de usuario y en la línea de comandos de la entrada HKCU Run — legibles para procesos del propio usuario, que es el mismo dominio de confianza que el fichero de config. No es un secreto frente a malware corriendo como el usuario; para ese modelo haría falta DPAPI/Windows Credential Manager (anotado como fase 2).
