## Modelo de amenaza

`sequences/` es configuración, pero configuración es superficie de ataque:
quien puede escribir allí (compromiso del repo de config, error de operador,
cadena de suministro) hoy puede degradar un motor en producción. El objetivo
de la ronda: **toda config hostil o errónea falla en carga, ruidosamente,
antes de degradar el proceso** — la misma filosofía fail-closed que ya aplican
las supresiones en arranque.

El lado RUNTIME ya estaba acotado por rondas previas (cap de 8192 estados,
`slim` del lastEv, state-key estructural anti-aliasing e ids duplicados
rechazados — 569b46c y anteriores). La superficie abierta era la **CARGA**.

## Vectores cerrados (cada uno con el fallo que causaba)

| Vector | Fallo que causaba | Mitigación |
|---|---|---|
| Fichero gigante | `os.ReadFile` no tiene límite: un YAML multi-GB se leía entero en memoria antes de cualquier check → OOM | `maxFileBytes` = 4 MiB, comprobado con `info.Size()` ANTES de leer |
| Anidación flow (`[`, `{`) | yaml.v3 decodifica por recursión y la anidación flow cuesta 1 byte por nivel: 4 MiB de `[` ≈ 4M niveles → agotamiento de pila = **crash del proceso**, no error de config | Pre-scan byte a byte, `maxNestingDepth` = 512. La anidación block (indentación) cuesta bytes cuadráticamente, así que el cap de fichero solo la deja en cientos de niveles |
| Nº de secuencias sin límite | `Observe` recorre TODAS las secuencias en cada hit: coste O(seqs × steps) sin techo | `maxSequences` = 512 |
| Pasos por cadena sin límite | La otra mitad del coste por hit | `maxStepsPerSequence` = 64 |
| Ventana absurda (`87600h`) | Cadena que nunca expira → un estado pineado por host para siempre → suficientes hosts y `maxTrackedStates` se agota → **pérdida de detección silenciosa** (el modo de fallo que más teme este repo) | `maxWindow` = 7 días; el error nombra la consecuencia |
| Runas de control en `id`/`name`/`tags`/`steps` | Llegan a logs, consola y webhooks a través de cada alerta: `\x1b` = inyección de terminal en los propios logs del engine (guiño al Artefacto A), `\n` = líneas de log falsificadas | Cap 128 runas (mismo estándar que las identidades del ingest: host 255 / user 256 / id 128) + cero runas Cc |
| Descripción gigante | Pinea KB por secuencia durante toda la vida del proceso | Solo longitud (512 runas): la descripción nunca sale del proceso (la alerta no la lleva), así que las runas de control se permiten ahí |
| Pasos fantasma (regla inexistente) | Cadena imposible de completar: en un host donde los DEMÁS pasos ya matchearon, el medio-estado queda pineado hasta que la ventana expire (y se rearma en el siguiente hit), contribuyendo en silencio al agotamiento de `maxTrackedStates` | `Manager.StepsWithoutRule(known)` + WARNING en el engine en arranque y en cada reload |

## Decisiones documentadas (para arbitraje si procede)

1. **Rechazo ruidoso vs. clamp silencioso**: elegido rechazar la carga
   entera. Un clamp (truncar ids, capar ventanas) transformaría un bug de
   config en un comportamiento casi-correcto que nadie investiga.
2. **Pre-scan de anidación deliberadamente naive**: cuenta corchetes
   estructurales también dentro de strings citados y clampea a cero en
   cierres sin apertura. Ningún atajo puede ocultar profundidad real (la
   anidación verdadera exige al menos tantas aperturas consecutivas como su
   propio nivel). Falso positivo teórico: una config con 512 `[` dentro de
   una descripción citada — no existe y el error lo explica.
3. **Reglas presentes pero deshabilitadas NO se reportan como fantasma**:
   deshabilitar una regla es decisión del operador; la cadena que espera por
   ella se reanuda en cuanto se re-habilita. Reportarlas sería ruido cada 15s.
4. **Sin campos nuevos en `/api/stats`**: f503b9d ya expone
   `correlator_states/sequences/cap`; los límites de carga se pinnearon como
   constantes exportadas (`MaxSequences`, `MaxStepsPerSequence`, `MaxWindow`,
   `MaxFileBytes`, precedentemente `MaxTrackedStates`).
5. **El WARNING de pasos fantasma se emite tras reload EXITOSO** (coherente
   con el resto del tick: carga fallida conserva el conjunto anterior).
