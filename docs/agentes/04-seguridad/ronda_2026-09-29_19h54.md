## Cambio 1 — Auth global en el webhook de salida (riesgo #1)

- **`internal/webhook`**: campo `token` + `SetToken()`/`TokenConfigured()`; `post()` añade `Authorization: Bearer <token>` en cada intento — incluidos los reintentos tras 5xx/429, que es donde una implementación descuidada perdería la cabecera. Sin token, cero cambios en el formato de red (despliegues loopback intactos).
- **`cmd/engine`**: flag `-webhook-token` con fallback `SF_WEBHOOK_TOKEN` (el flag gana, mismo orden de resolución que el token de ingest). El banner de arranque ahora distingue los dos estados: `Authorization: Bearer enabled` o recordatorio explícito con el flag y la env var.
- **Semántica deliberada**: el token global solo aplica al conector de nivel engine; los `actions.webhook` por-regla conservan su `secret` independiente. Ambos caminos nunca se mezclan, y el README lo documenta.
- **Tests nuevos** (2): `TestSendsBearerTokenWhenConfigured` (cabecera correcta + reenvío en el reintento tras 5xx) y `TestOmitsAuthHeaderWithoutToken` (sin cabecera cuando no hay token).

## Cambio 2 — Rotación de token de ingest sin downtime (riesgo #2)

- **`internal/ingest`**: `SetPreviousToken()` registra el token anterior, válido junto al actual hasta el reinicio del proceso; `tokenMatches()` compara contra ambos con `crypto/subtle` y combina los resultados con OR aritmético (`(cur | prev) == 1`), sin cortocircuito, para no filtrar por tiempos cuál token coincidió. Guardas: la ventana se ignora si no hay token primario, si el anterior está vacío o si es igual al actual. `Rotating()` expone el estado para el banner.
- **`cmd/engine`**: flag `-token-previous` con fallback `SF_INGEST_TOKEN_PREVIOUS` (el flag gana). El banner distingue `rotation window OPEN` (migración en curso, instrucciones incluidas) del arranque normal.
- **Procedimiento operativo** (documentado en el README, tres pasos): arrancar con ambos tokens → redeplegar sensores con el nuevo (orden libre, sin pérdida de eventos) → reiniciar solo con el nuevo. La ventana se abre por reinicio, no por timeout: nada caduca bajo carga.
- **Tests nuevos** (4): token viejo aceptado (con contador `rejected` en 0), token nuevo aceptado en paralelo, intruso rechazado exactamente igual que fuera de ventana, y las tres guardas de `SetPreviousToken`.

## Cambio 3 — Revisión de superficie de `actions` (SSRF)

Verificación realizada antes de documentar: las URLs y secretos de acción provienen exclusivamente de los YAML del directorio de reglas (`rules.LoadDir` al arranque; el hot-reload lee el MISMO directorio resuelto), la API HTTP es de solo lectura y no puede crear reglas, y el tráfico de sensores nunca alcanza la configuración de acciones. Conclusión: **no existe ruta de entrada no confiable** que pueda apuntar un webhook a un servicio interno; una URL interna es una decisión del operador, no un vector de inyección. Documentado como párrafo "Trust model" en el doc comment de `internal/actions/actions.go` para que la conclusión sobreviva a futuros refactors. Si en fase 2 la API adquiriera escritura de reglas, este párrafo es el punto exacto a re-abrir.
