## 2. Hallazgos y fixes (todos con prueba antes/después)

### F1 — El trap del EXIT ejecuta `kill 0` si el fallo llega antes de arrancar el engine — CORREGIDO

`trap 'kill "${ENGINE_PID:-0}" ...'`: el `:-0` evita el error de variable vacía, pero `kill 0` en bash **señala al grupo completo de procesos** del script. Con un fallo antes de L44 (p. ej. `go build` roto, que es justo el caso en que el engine nunca arrancó), el script se mataría a sí mismo con SIGTERM en lugar de propagar su código de error real — y sin job control el grupo puede incluir al llamador. **Prueba** (grupo aislado con `setsid`): trap original → `rc=143` (Terminated, el error real desaparece); trap parcheado → `rc=1` limpio. **Fix**: guard de presencia `[ -n "${ENGINE_PID:-}" ] && kill ...` — solo se señala un pid que existió.

### F2 — Sin pre-flight de puerto: un stack ya levantado hace que el bench mida el engine VIEJO atribuyéndole los números al nuevo — CORREGIDO

La espera de salud (`curl /api/health` en 7778) responde al instante si **cualquier** engine ya está escuchando — el desarrollador con el stack de desarrollo arriba, o un run anterior no limpiado. El engine recién construido muere sin poder bindear, el health check ya pasó, y el bench mide el binario viejo (otra versión, quizá con `-store` distinto): **números válidos, atribución falsa** — el peor modo de fallo para un instrumento de medición, porque no falla: miente. La ronda 09h37 documentó el requisito "ports free" en el comentario, pero el script no lo verificaba. **Prueba**: engine real arriba en 7777/7778 → script parcheado aborta con exit 1 y mensaje explícito ("measuring the wrong binary would fake the numbers"); el puerto queda intacto (no mata el stack ajeno). **Fix**: pre-flight antes del build — si 7778 ya sirve `/api/health`, abortar. El check de 7778 con `-f` cubre exactamente el camino silencioso (un engine completo viejo ocupa ambos puertos; un ocupante raro de solo-7777 conduce a "never became healthy" → rojo limpio, camino ya correcto).

### F3 — Bench "exitoso" sin muestras parseables → veredicto NO SAMPLES pero línea final `OK (advisory bench recorded)` y exit 0 — CORREGIDO

Si el formato del reporte de `cmd/bench` deriva (o el fan-out SSE se rompe de forma que no produce latencias), `p99_us` queda vacío: el script emitía un `::warning::` y **terminaba en verde diciendo "OK (advisory bench recorded)"** — contradiciendo su propia filosofía: los números que desaparecen silenciosamente son un fallo de completitud del instrumento, análogo a las alertas perdidas, y deben poner el run rojo para merecer acta. Con `-n 2000` fijo no existe camino legítimo a RC=0 sin muestras. **Prueba** (copia stub del script con un bench que imprime `RESULT OK` sin latencias, ejecutada desde la profundidad correcta del repo): pre-parche → `EXIT=0` + "OK (advisory bench recorded)"; parcheado → `EXIT=1` + FAIL explícito. **Fix**: ese camino hace `exit 1` con diagnóstico (format drift / SSE fan-out). El `::warning::` de "sin muestras" desaparece: lo reemplaza el rojo.

### O1 — `to_us` interpola el valor dentro del programa awk sin validar formato — DOCUMENTADA, sin código

`awk "BEGIN{printf ... ${v%ns} ...}"`: `$v` viene del reporte del bench (binario del repo, cadena de confianza local — no entrada hostil del wire), así que no es alcanzable por un atacante; el riesgo sería un reporte corrupto que rompa la sintaxis del awk (con `set -e` → rojo ruidoso, no silencio). Una validación `^[0-9.]+(ns|us|ms|s)$` antes del `case` cerraría la puerta por defensa en profundidad; se deja anotada para la próxima ronda que toque el script (el test de sufijos de la 09h37 ya la cubriría).
