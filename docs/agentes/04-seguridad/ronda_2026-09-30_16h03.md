## 2. F1 — el proxy ignoraba `SF_API_TOKEN` (defecto #27, funcional, media)

**Causa raíz.** El README (§auth) promete: «The console-service bridge honors the same `SF_API_TOKEN` variable, so a token-protected console stack needs exactly one extra environment entry». La promesa es cierta para el bridge de `web/console-service` (`bridge.ts:33` lo honra) — pero **falsa para la consola Next.js**: `route.ts` no leía la variable y reenviaba cada petición sin `Authorization`. Consecuencia: el operador que endurece el engine con `-api-token` (la única vía documentada para binds no-loopback) deja la consola **clavada en 401s silenciosos** — y el «arreglo» que descubre el operador es desarmar la API. Es la clase de defecto que castiga exactamente la postura segura.

**Fix.** Lectura perezosa de `SF_API_TOKEN` en cada petición reenviada (GET y POST) y cabecera `Authorization: Bearer …` adjunta cuando existe — el mismo contrato que el bridge. Cero cambios en el engine.

## 3. F2 — el límite del proxy no heredaba la postura del engine (defecto #28, brecha de postura, alta)

**El hueco, en dos capas.**

1. **Lectura de telemetría más allá de loopback.** `next dev` bindea en `::` — verificado en el live-fire de esta ronda: el banner imprime `Network: http://21.0.7.64:3000`. El proxy reenviaba `/api/engine/*` a `127.0.0.1:7778` **desde cualquier Host**: cualquier vecino de red alcanzaba la telemetría (eventos, alertas, hosts calientes, exportaciones) sin credencial — saltándose por completo la postura del engine, que para eso exige token o loopback. Y como el Host lo elige el cliente, una página con DNS rebinding alcanzaba el proxy como «mismo origen», leyendo también desde el navegador de la víctima.
2. **Escritura de triaje drive-by (CSRF).** El handler del engine (`handleAlertStatus`, api.go:690-699) parsea el cuerpo con `json.Unmarshal` **sin exigir Content-Type** — y la petición cruzada con `content-type: text/plain` es una *simple request* que no necesita preflight CORS. Una página hostil abierta en el navegador del operador podía `POST http://<consola>:3000/api/engine/api/alerts/<id>/status` con `{"status":"closed"}` y mover el triaje sin ningún indicio (la respuesta no se lee, pero el estado sí cambia).

**Fix (en el proxy, no en el engine — el límite es suyo).** Dos guardas en `refused()`, por delante de todo reenvío:

- **Fijación de Host:** solo se sirve a `localhost`/`127.0.0.1`/`::1` (comparación de hostname sin puerto, brackets IPv6 y punto final normalizados). Despliegues no-loopback: `CONSOLE_ALLOWED_HOSTS` explícita, con 403 que **nombra la válvula de escape** — fail-loud, el mismo estándar del warning del engine al bindear `0.0.0.0` sin token. La fijación de Host mata el rebinding (lectura y escritura).
- **Escritura same-origin:** el POST de triaje se reenvía solo sin evidencia de contexto cross-site (`Origin` que no coincida con el Host de la petición, o `Sec-Fetch-Site: cross-site`). Los clientes sin cabeceras de navegador (curl, los smokes de la casa) siguen funcionando: sin contexto de navegador no hay CSRF que defender. El `Origin` malformado se rechaza — nunca se reenvía en su nombre.

El contrato de solo-lectura queda intacto (405 `read_only` en el resto de escrituras) y la respuesta 403 lleva `host` + `hint` accionable.
