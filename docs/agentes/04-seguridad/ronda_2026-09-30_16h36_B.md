## 2. Defecto propuesto #31 — secreto de canal en el log de entregas fallidas (ALTA)

**Descripción.** Toda entrega HTTP fallida por transporte (timeout de 5 s, DNS, conexión rechazada — el camino de fallo NORMAL del canal, no un caso raro) imprime en el log del engine la **URL completa del endpoint**, y en los canales C2 la URL ES el secreto o lo porta:

- `internal/notify/http.go:45-47`: `hc.Do(req)` falla → Go envuelve el error en `*url.Error` (contrato de `net/http`: "Any returned error will be of type *url.Error"), cuyo `Error()` es `fmt.Sprintf("%s %q: %s", e.Op, e.URL, e.Err)` — **imprime la URL íntegra**. El error se devuelve crudo dentro de `deliveryError`.
- `internal/notify/notify.go:217`: `log.Printf("[NOTIFY %s] delivery failed: %v", ...)` lo vuelca al log. Para **Telegram**, la path lleva el token del bot (`channels_http.go:100`: `apiURL + "/bot" + t.token + "/sendMessage"`); para **Slack**, el hook URL es la credencial (channels_http.go:28-30 lo dice textualmente).
- Misma mecánica en el error de construcción (http.go:38-40): `http.NewRequestWithContext` falla en `url.Parse`, que también devuelve `*url.Error` con la URL citada dentro.

Cada reintento fallido escribe el token en el log. Con logs que viajan a journald, un collector, o al propio SIEM, el secreto de notificación se propaga fuera del proceso. Es exactamente la clase de fuga que el estándar de la casa (secretos SIEMPRE por entorno, jamás en texto plano) persigue — aquí el secreto está bien guardado en config y mal tratado en el camino de error.

**Evidencia (lectura de fuente + contrato stdlib, no display):** `grep -n "bot" internal/notify/channels_http.go` → 1 construcción con token en path; `grep -n "delivery failed" internal/notify/notify.go` → 1 sitio con `%v`; `grep -n "err: err" internal/notify/http.go` → 2 envolturas crudas (líneas 40, 47). El comportamiento de `*url.Error` es contrato estable de stdlib. La prueba falsable para el aterrizaje está en §2-bis.

**Alcance de la clase (pre-existente, mismo fix):** la asunción "la URL no es secreta" era razonable antes de C2 y hoy ya no lo es:

| Sitio | Fichero:línea | Qué filtra |
|---|---|---|
| notify transport | `internal/notify/http.go:40,47` → `notify.go:217` | token Telegram / hook Slack completos (ALTA) |
| webhook de SIEM | `internal/webhook/webhook.go:146` + `164` | `c.url` literal en el log + `lastErr` crudo (`*url.Error`) — URLs con credencial en query/path (media) |
| webhook por regla | `internal/actions/actions.go:219` | `err` crudo → URL completa de la regla (media) |
| banner de arranque | `cmd/engine/run.go:425,427` | `o.webhookURL` literal (baja: consola del operador, pero misma clase) |

El canal **email es seguro** por construcción: dial a `host:port` y errores SMTP (`535 auth...`) no contienen credenciales — verificado en email.go:77-144.

**Solución (parche exacto para 02-A).** Un helper en `internal/notify` (o compartido si 02-A prefiere una sola fuente; sugerencia: `internal/notify/http.go` y duplicación mínima comentada en `webhook.go`/`actions.go`, o un `internal/httppath` diminuto — su decisión):

```go
// redactedEndpoint keeps scheme://host and drops path and query:
// Slack hooks and Telegram bot paths ARE the credential.
func redactedEndpoint(raw string) string {
        u, err := url.Parse(raw)
        if err != nil {
                return "endpoint-no-parseable"
        }
        return u.Scheme + "://" + u.Host
}

// transportErr strips the *url.Error wrapper (its Error() prints the
// full request URL) and keeps only the underlying cause, which names
// the network problem and never the credential.
func transportErr(endpoint string, err error) error {
        var ue *url.Error
        if errors.As(err, &ue) {
                err = ue.Err // "context deadline exceeded", TLS dial errors, ...
        }
        return fmt.Errorf("post %s: %w", redactedEndpoint(endpoint), err)
}
```

Aplicación: (a) `http.go:38-47` — ambas ramas devuelven `transportErr(url, err)` (cubre también el parse error: `url.Parse` ya devuelve `*url.Error` y `ue.Err` es la causa limpia sin citar la entrada); (b) `notify.go:217` queda intacto porque el error ya llega saneado; (c) `webhook.go:164` envuelve igual y `:146` cambia `%s` de `c.url` por `redactedEndpoint(c.url)`; (d) `actions.go:219` envuelve el error de `Do`; (e) `run.go:425,427` imprime `redactedEndpoint(o.webhookURL)` (el valor diagnóstico scheme://host se conserva). `Endpoint()` se queda como está: diagnóstico in-process, no log.

2. Unit: endpoint con carácter de control (parse error) → mismo par de aserciones (la entrada no aparece citada).

4. Análogo en `webhook` y `actions` (un caso cada uno).
5. E2E: `smoke_notify.sh` ya tiene el caso "dead relay" — añadir la aserción de que el log del engine no contiene la path secreta del mock. Es la prueba de la casa: barata, en caliente, y cubre la integración real.

## 3. Defecto propuesto #30 — CSV de eventos: `process_name` y `file_path` sin neutralización de fórmulas (media)

**Descripción.** El contrato del paquete de export (export.go:1-7) declara que las celdas CSV controladas por el atacante "never open with a character a spreadsheet would interpret". El CSV de **alertas** cumple: `csvSafe` en host, user, summary, message, status_note, status_by (export.go:94-97) y lo TESTEA (`export_test.go:102-104`, aserción del `=` prefijado en summary). El CSV de **eventos** NO cumple en dos celdas de telemetría atacante:

- `export.go:172` — `eventProcessName(ev)` escribe `ev.Process.Name` **crudo**. Un nombre de proceso es un nombre de fichero elegido por el atacante: `=mal.ps1`, `+x.js`, `-rf.bat` son nombres legales en Windows y Linux. Esa celda abre una fórmula al abrir el export en una hoja de cálculo — el vector clásico de inyección CSV en tooling SOC (el propio docstring lo cita como motivación).
- `export.go:175` — `eventFilePath(ev)` crudo (defensa en profundidad: una path suele empezar por unidad/slash, pero el invariante del paquete no distingue).

Las celdas restantes crudas son seguras por procedencia: `id`/`timestamp`/`type`/`source` (engine), `host`/`user` ya neutralizados, `process_pid`/`network_port` numéricos, `network_destination` (IP; un dominio conforme a RFC no empieza por `=+-@`), `registry_key` (prefijo HKLM/HKCU). En el CSV de alertas, `rule_name`/`tags` vienen del directorio de reglas del operador — misma procedencia que `type`/`source`, correcto dejarlos crudos.

**Severidad: media.** Requiere que el analista abra el CSV en una hoja de cálculo, pero el evento puede provenir de un sensor REMOTO (el ingest acepta telemetría de red autenticada) — la estación del analista es un límite de confianza distinto del host que generó el evento, que es exactamente el escenario para el que existe `csvSafe`.

**Parche exacto (2 líneas) + test (para 02-A o 04-A):**

```diff
-                               eventProcessName(ev),
+                               csvSafe(eventProcessName(ev)),
...
-                               eventFilePath(ev),
+                               csvSafe(eventFilePath(ev)),
```

## 4. Observaciones registradas (sin defecto)

- **Política http:// en canales HTTP (media-baja, coherencia).** El canal email rechaza el claro loud ("alert content must not ride an unencrypted hop"); slack/telegram aceptan `http://` a cualquier host (config.go:214 solo exige http(s)). Para un hook Slack o un Bot API no-loopback en claro, el secreto-URL y el contenido viajan sin cifrar — el estándar del email no se aplica al resto. Sugerencia para 02-A (no bloquea C2): fail-loud para `http://` no-loopback, o warning de arranque + párrafo en README. El `api_url` self-hosted de Telegram en loopback queda legítimamente cubierto por la excepción loopback.
- **`drain()` y el deadline de 2 s (baja, semántica).** El deadline se comprueba tras cada entrega; una entrega SMTP (15 s) puede llevar el drain real a ~2 s + 15 s. Documentado como "best-effort bounded" — correcto en espíritu, impreciso en cifra; ni siquiera es de seguridad.
- **Para 02-B (TS, observaciones de mi barrido de consola-service):** (1) `bridge.ts` `pumpSSE` acumula `buf` sin techo hasta el próximo `\n\n` — fuente de confianza en loopback, pero es la clase "parked bytes" que la casa cazó dos veces; un techo con desconexión sería barato si algún día se toca el bridge. (2) `analyst.ts` lee `res.json()` sin techo de tamaño — el proveedor lo configura el operador; observación igualmente. (3) La inyección de prompts vía texto de eventos hacia el panel del analista es inherente al feature (el operador pide interpretar telemetría hostil); el dato útil es que la salida se renderiza como texto React (auto-escape) — sin superficie XSS adicional. El resto del barrido (hub.ts: validación de payload, limiter por socket, GET-only, CSP estricta, `esc()` en toda interpolación de la página de estado y not-found) está limpio y se ratifica.
- **`internal/webhook` (resto):** Go strippea `Authorization` en redirecciones cross-host (clientes por defecto) — el token no sigue al receptor que redirija; cuerpo no reenviado salvo 307/308 same-host. Limpio.
- **`internal/api/filters.go` + `internal/store`:** `\x1f` stripped en el chokepoint compartido, `likeNeedle` escapa `\ % _` con `ESCAPE '\'`, severidades whitelisted, `limitFrom` digits-only con clamp 1000, exports bajo `h.auth` (solo `/api/health` exenta, api.go:114). Limpio — el carril TS/Go de lectura de datos está bien defendido.
