## 3. Defecto propuesto **#33 (baja, latente)** — `postBatch` pierde el conteo de no-codificables en las ramas permanentes si el lote mezcla

- **Dónde:** `internal/siem/elastic.go` — las dos ramas que 2bc7391 hizo permanentes devuelven `len(batch)` como rejected: el hunk del build error (`return 0, nil, len(batch), rerr`) y el `default` del switch de estado. En ese punto `batch` ya fue reasignado al **wire** (línea `batch = wire`), y la variable local `rejected` acumula las alertas **no codificables** que el wire excluyó.
- **Consecuencia:** si un lote mezcla no-codificables con codificables y la respuesta es un 4xx (o el build falla), las no-codificables **no cuentan en ningún contador de vida** — `sent`/`failed`/`dropped` quedan por debajo de las alertas consumidas. Subconteo silencioso, la propiedad exacta que el propio parche declara querer preservar ("contadores honestos... en UN pase").
- **Por qué "latente" y no vivo:** con el esquema actual de `alert.Alert` (todo `string`/`bool`/`[]string`/`map[string]string`), `json.Marshal` no puede fallar → `rejected == 0` siempre → `len(batch)` es hoy equivalente al conteo honesto. Pero el paquete **defiende explícitamente** la rama (el `rejected++` y el error "no encodable alerts in batch" existen), y el esquema ha crecido históricamente (`Enrich`, `Notify`, `Message` entraron por versiones): el primer campo futuro no-marshalable resucita el subconteo. La defensa existe y está coja en la mitad de sus ramas.
- **Parche exacto (2 tokens, 2 sitios):**

```go
// internal/siem/elastic.go, postBatch — build error:
return 0, nil, rejected+len(batch), rerr
// internal/siem/elastic.go, postBatch — default (4xx no-429):
return 0, nil, rejected+len(batch), fmt.Errorf("cluster answered %d", resp.StatusCode)
```

- **Falsabilidad — declarada honestamente por lectura:** con el esquema actual NO existe input construible que dispare la rama (un test rojo exigiría fabricar un `Alert` no-marshalable, imposible con campos todo-string). Es el mismo criterio declarado para las líneas de banner sin instrumentación de captura: la falsabilidad aquí es la auditabilidad del flujo de contadores en fuente, que es de 3 líneas. Si 02-B prefiere blindaje con test, el camino es un test white-box con un marshaler inyectable — lo considero sobre-ingeniería para una rama defensiva y lo dejo anotado.

## 4. Nota de método para la checklist O4 (mi ronda 17h25): la sutileza `Op:"parse"`

El barrido de clase de la sesión hermana 17h40_B y el mío coinciden (clase #30 muerta en el árbol Go). Esta ronda añade el mecanismo que ambos barridos daban por supuesto y conviene dejar escrito: **los errores de `http.NewRequest` SON `*url.Error`** (con `Op: "parse"`), así que un error de parseo que ecoa la URL cruda **también** queda cubierto por el unwrap de `redactedErr`/`redacted` en el sitio de log — no hace falta redactar en retorno para estar cerrado (webhook/siem redactan en log; notify/actions en retorno; ambas formas son cerradas). Un barrido futuro que encuentre `return ..., err` sin envolver en un camino de NewRequest **no debe** clasificarse solo por lectura del return: mirar dónde imprime el llamador. `cmd/bench` queda examinado y fuera de alcance (GET de instrumento, token en header, sin secretos en URL) — mismo veredicto de 17h40_B.
