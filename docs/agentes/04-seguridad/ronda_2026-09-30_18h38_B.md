## 3. Hallazgos nuevos

### F1 (baja) — keys React duplicadas en la cola cuando el followup cae en la misma ventana

`respond-view.tsx:182` usa `key={r.action_id}`, pero el flujo Kill certificado escribe DOS líneas JSONL con el MISMO `action_id` cuando la señal falla tras el commit: la pre-señal (`decision=executed`, el compromiso) y el followup (`decision=denied`, `followup=true`, `respond.go:330-336` — `follow := rec` copia la ActionID). Ambas líneas se escriben consecutivas y caerán juntas en cualquier cola de 100/500 → keys duplicadas: React puede renderizar filas erróneas o lanzar warning de integridad — en la vista que existe para mostrar la prueba forense. Parche de 1 token: `key={\`${r.action_id}:${r.followup ? 'f' : 'p'}\`}` (o índice compuesto). Falsabilidad: un kill que falle post-commit (reciclado entre las dos lecturas de nombre) con la consola abierta en la cola.

### F2 (media-baja) — la rama followup no tiene cobertura en ningún nivel

`rg Followup --type go` solo encuentra el código de producción: ni tests unitarios del paquete respond, ni e2e (`e2e_respond_kill.sh` no la menciona), ni la consola la ejerce. Es LA línea JSONL que registra "comprometido pero no aterrizado" — el único rastro del modo de fallo que la propia grabación temprana de la clave de idempotencia (compuerta 17h35 §1) diseñó para dejar prueba. El 409 del reintento está testeado (`TestIdempotencyRepeatedDenied`, camino éxito→reintento), pero nadie afirma hoy: (a) que el fallo post-commit escribe el followup con `code`+`mechanism`+`fallback_reason`+`followup=true`, ni (b) que el reintento tras un kill FALLIDO también recibe 409 (la clave quedó comprometida aunque la señal no aterrizara). Propuesta de cobertura: test unitario que fuerce `killVerified` fallido tras commit (name-flip entre las dos lecturas) + aserción del par de líneas; y la fase e2e correspondiente. Sin urgencia de hotfix (el código leído es correcto) — es deuda de falsabilidad en la superficie destructiva, no defecto vivo.

### O1 — tarjeta armada obsoleta tras un restart sin flags con la consola abierta

El stream declara su trade-off (comentario en `use-engine-stream.ts`): un poll que recibe 404 conserva el último estado conocido — "nunca un fake clear de un motor armado". Correcto para hicups y para el armado estático del proceso; el hueco es el restart del engine SIN flags con la consola abierta: `status='live'` (stats sigue 200) y la vista seguiría mostrando la tarjeta armada con recuentos congelados. Iteración posible: distinguir 404 persistente con `status='live'` (clear) de fallos transitorios (conservar). Declarado por 02-B como decisión consciente — se registra, no se reabre.
