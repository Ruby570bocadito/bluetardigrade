## Corrección aplicada

### `analyst:ask`: la copia de reserva del cliente se limpia campo a campo — severidad: media-baja

- **Descripción:** el camino de incidentes validaba cada campo de las
  alertas del cliente (`validateIncidentPayload`: tipos, recortes,
  descarte de campos desconocidos), pero el camino de alerta única
  aceptaba la copia del cliente tal cual cuando la alerta ya había
  salido del anillo del hub: un campo desconocido (`injected: ...`)
  viajaba literalmente al prompt del proveedor y valores mal tipados
  se colaban sin mensaje.
- **Causa raíz:** el flujo de alerta única es anterior al de
  incidentes y quedó con la validación mínima (`rule_id`) cuando el de
  incidentes endureció su entrada; ambos comparten el mismo presupuesto
  y el mismo prompt, no la misma higiene.
- **Solución:** la limpieza campo a campo se extrae a
  `cleanAlertObject` (solo campos conocidos, cadenas recortadas y
  clampeadas, arrays filtrados y acotados, atributos solo de cadenas)
  y `validateAnalystAlert` la expone para el camino de alerta única;
  `validateIncidentPayload` reutiliza el mismo helper (una sola
  definición de higiene). `hub.ts` conserva la política de copia
  autoritativa (la copia del motor gana mientras el id siga en el
  anillo) y aplica el validador solo a la copia de reserva; los
  mensajes de error que fijan los tests y el orden de los presupuestos
  no cambian.
- **Tests:** `analyst.test.ts` añade tres casos unitarios del
  validador (rechazo de no-objetos y `rule_id` vacío, clamps y
  defaults, caída de campos desconocidos) y `hub.test.ts` uno de
  integración: el prompt del proveedor no contiene el campo forjado.
  Demostrado que antes del cambio ese test fallaba
  (`(fail) analyst:ask cleans the client fallback copy...` en
  hub.test.ts:388 contra el código previo) y que con el cambio la
  batería completa está en verde.
- **Cómo verificarlo:** `cd web/console-service && bun install
  --frozen-lockfile && bun test && bunx tsc --noEmit`.
